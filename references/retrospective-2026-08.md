### L1 长期文档必须用**用户本人身份**创建，不能用机器人身份
- **场景**：08-11 v0 文档用机器人应用权限创建（author ID 是机器人），产品负责人在文档里只是协作者。后果：旧页删不掉、无删除权限、右键没有删除选项，最后只能整体废弃重建。
- **错误做法**：MCP 机器人创建文档省事，长期知识库文档也这么干。
- **正确做法**：一次性/临时文档可以用 MCP 机器人；**给用户长期用的正式文档必须用用户浏览器 cookie（per-user 通道）创建**，所有者是用户本人。
- **规则**：创建正式文档前先问一句"这文档谁拥有"，只要答案不是机器人，就走浏览器 per-user 通道。

### L2 `listAfter` 是 PREPEND：按源树顺序正序创建 = 顺序全反
- **场景**：08-12 副本 130 页顺序全乱，产品负责人指出"顺序跟飞书知识库不一致"。
- **根因**：`listAfter`（operation=4）语义是"插到列表头部"，不是"追加到尾部"。按飞书顺序正序创建，最终顺序完全颠倒。
- **规则**：用 listAfter 批量建页**必须按源树逆序提交**；或建完立刻 readback 比对顺序，不能提交完就信。凡"顺序"类需求，验收标准必须是 readback 后逐位比对，不是 API ret=0。

### L3 同一要求被用户重复提出 ≥2 次 = 流程性缺陷
- **场景**：sheet 页表格要"在页面里插入原生表格"这个要求，产品负责人 08-12、08-14、08-22、08-24 说了**至少 4 遍**才彻底落实。
- **错误做法**：每次口头答应，下轮同步脚本没把要求固化进代码，导致下次重建又丢。
- **正确做法**：用户对产出形态的要求（表格用什么块、标题用什么样式）必须**写进同步脚本 + 任务护照（TASK-SOP.md）+ skill**，三处固化才算落实。口头确认不算落实。
- **规则**：用户纠正过的产出形态要求 → 当场固化到脚本/文档，下次迭代前 grep 任务护照确认还在。

### L4 删除文档 ≠ 清空内容，"删了"必须 readback 验证
- **场景**：08-12 晚清理无用文档，"已删除"报了三次，产品负责人三次问"真的删了吗？我还能看到"。
- **根因**：API ret=0 不代表删除生效（假成功）；webdisk 列表有缓存；回收站机制导致"列表里没了但用户还能打开"。
- **规则**：任何删除/清理操作，验收 = **readback（列表 + 打开目标 URL 确认状态码/内容）**，不是 API 返回。删正式文档前必须列"ID→标题→用途"对照表经用户确认（产品负责人规则 2026-08-14）。

### L5 多文档并存时必须有台账，操作前报目标 ID
- **场景**：08-13 上午多文档并存（v0/v1/v2/测试文档），主控 Agent搞混目标，在 A 文档上操作，产品负责人在问 B 文档。原话："你搞的文档，你不发给我，我不知道你在搞另一个文档"。
- **规则**：**文档操作开工前，先把目标 URL/ID 发给用户确认**（产品负责人规则 2026-08-14 ③）；多文档并存时维护一张活台账（ID→标题→状态→用途），每次操作对台账。临时文档加 `_test_` 前缀。

### L6 MCP 图片上传 701451 = 账号级配额，浏览器 API 不受限
- **场景**：08-13 批量传图报 701451，一度误判为"文档级限制"。
- **真相**：701451 和 850005 是 MCP 机器人 API 专属限制；浏览器原生 `doc_img_upload`（走 cookie）不受影响，实测 50 张连传零失败。
- **API**：`POST https://doc.weixin.qq.com/diskthumb/doc_img_upload?globalPadId={docid}&sid={sid}&wedoc_xsrf=1`，body=multipart(file)，返回 body.url 即 CDN URL。
- **规则**：批量图片操作直接走浏览器 cookie API，别碰 MCP 配额。

### L7 sheet 页读取端点：v3 404，必须用 v2
- **场景**：08-18 排查发现设备型号说明/产品关系适配表两页长期空壳，根因是 sheet 数据读取用了 `/sheets/v3/.../values/`（404 不存在），换 v2 端点才拉到 9313/7406 字符真实数据。
- **附加坑**：`grid_properties` 谎报行列（报 199×21，实际 22×9 / 28×5），必须按非空行列截断，否则表格 mutations 从百级爆炸到 11630。
- **规则**：读飞书 sheet 走 v2 values 端点；建表格块前先算真实非空行列。

### L8 Markdown 样式残留：`strip_markdown()` 必须在分段前执行
- **场景**：08-14 产品负责人反馈"标题没有变成标题的样式，很多样式都是 Markdown 的样式""表格的表头还在最后一行"。
- **根因**：raw markdown 直接写块没清洗；flush_text 分段逻辑与 strip 顺序不对。
- **规则**：raw markdown → blocks 转换必须：①先 `strip_markdown()` 去 **bold** 等标记 ②按空行分段 ③列表项独立成块 ④**bold 整行用 bold=True 的 create_text_block。转换后抽 3 页 readback 肉眼比对样式属性。

### L9 SmartPage 标题块 type=12-17（不是 3-8），缺 render_mode=1 假成功
- **场景**：08-17 标题修复，skill 之前记录的 type=3-8 全错，实测 H1=12/H2=13/H3=14，且必须 `render_mode=1` + `attribs='+b'`，缺任一个 API ret=0 但块不生效。
- **规则**：任何 block 类型/参数结论必须实测 readback 后才写入 skill；skill 里的类型表是猜的还是实测的，写明来源。

### L10 飞书 Wiki API 的 parent_node_token 有坑：字段名 `_parent_node_token`
- **场景**：08-18 同步只拉到 20 个根节点，曾误判"飞书 API 有 bug 拉不到子节点"。
- **真相**：BFS 遍历字段名写错（`parent_node_token` → 应为 `_parent_node_token`）+ 无 visited 去重（20 节点重复成 360）。修对后 130+ 节点全拉到。
- **教训**：报"外部 API 有 bug/不支持"之前，先证明自己参数对了——换字段名、加日志打印原始响应。这是「搜不到先证明搜对了地方」的 API 版。

### L11 多用户身份隔离：MCP 应用 token ≠ 用户权限
- **场景**：08-18 产品负责人要求 skill 支持多用户，"不要让其他人用到某个用户的权限"。
- **落地**：双通道架构——MCP（机器人身份）+ 浏览器 per-user cookie（`~/.hermes/identity/wecom/{principal_id}.json`）。正式文档读写、图片上传走 per-user；机器人只干中立任务。
- **规则**：见 SKILL.md「身份隔离」章节。核心：per-user cookie 文件放对目录（08-20 有两个成员凭证放错目录的事故）。

### L12 全量重建的代价：能增量就别重建
- **场景**：08-21 产品负责人批准"新建干净文档全量重建"方案（v3），代价是图片重新去重上传（1135 张 555MB）、52 个表格页重建、79 批 mutations。
- **何时该重建**：当页面结构层（顺序/层级/块类型）烂到修不动时。v3 重建后 fidelity 100。
- **何时不该**：内容层小错（个别页乱码/占位符）→ 单页修复，别动整树。**单页重建会膨胀 children**（2026-08-19 #133-135），反复重建同一页越搞越大。

### L13 权限变更产生待发布，但不推进版本号 → 验证逻辑假绿
- **场景**：08-24 产品负责人邀请成员（仅浏览）后文档进入待发布态，但 pad_ver 停在 1950。发布验证脚本用「pad_ver == 发布version ⇒ 无待发布」短路判断，cron 连续多轮报"一切正常"，实际面板显示"有未发布的改动"。
- **根因**：内容变更会推进 pad_ver，**权限变更等编辑器外操作只置 pending 标志不推版本**。用版本号判断发布状态存在盲区。
- **修复**：UI 发布器 v2 每次打开分享面板，「再次发布」按钮存在就点；成功判据 = version 推进 **或 publish_time 推进或面板态清空**；worker 每轮都跑 publish-verify（无待发布时秒回）。
- **规则**：**任何"状态一致性"验证不能只依赖单一指标**（版本号），必须交叉（版本号 + 时间戳 + 面板态）。"两次读数相等"≠"状态一致"。

### L14 字号变大 = 客户端缩放，先查数据层再下结论
- **场景**：08-24 产品负责人"不知道碰了哪，字号都变大了"。排查：pad_ver 未变 + 全 130 页 attribs 扫描干净（无字号属性）→ 数据层无变化 → 客户端显示层缩放（Ctrl+滚轮误触）。解法 Ctrl+0。
- **规则**：用户报告"文档坏了"类问题，先查数据层硬指标（版本号、属性扫描）排除数据损坏，再指向客户端。同理适用"图片不显示"（先查 CDN URL 是否有效）。

## 二、行为级教训（跨任务通用）

### B1 「完成」必须 readback 验证，API ret=0 不算数
- 三周里被纠正最多的一条：删除假成功（L4）、写入假成功（L9 render_mode）、发布假绿（L13）、API 写 internal_auth ret=0 但读回不变（08-24 权限）。
- **规则**：每个写操作后跟一步读回；读回和写操作必须在同一次执行里闭环，不能"下次再看"。

### B2 用户重复纠正同一类问题 = 流程缺陷，不是执行失误
- 表格形态（4 次）、完成度检查（8-13/8-14 "都解决了吗"×N）、文档台账（L5）。
- **规则**：同类纠正 ≥2 次时，停止在执行层打补丁，升级到流程层：把要求固化进脚本默认行为 + 任务护照 + skill 检查清单。

### B3 先建台账/清单，再动手；开工先对目标
- 多文档混淆（L5）、v2/v3 并存期误操作、删除前列对照表（产品负责人规则）。
- **规则**：多对象任务第一步永远是盘点（有几个、哪个是哪个、要动哪个），盘点结果落盘并同步用户。

### B4 修复 → 验证 → 查下游 → 清旧数据 → 等定时确认 → 查监控
- 修复铁规（memory 已有），三周里每一条都被用到：08-24 publish 三件套修复后，下一轮 cron 12:20 是验证点。
- **规则**：改生产脚本必须走完整闭环，"改了+语法过了"只是第 2 步。

### B5 假成功的 API 特征清单（企微专属）
- `sp_submit` 无 render_mode/attribs → ret=0 块不生效
- `listRemove` 删页面内部 children → ret=0 删 0 个
- `file_modify_secure_setting` 改 internal_auth → ret=0 读回不变（服务端静默忽略）
- `webdisk/list` file_status 参数 → 被忽略
- children 重排 operation=6/7 → ret=0 顺序不变
- **规则**：企微 HTTP API ret=0 只是"请求被受理"，**必须 readback**。这个清单在持续增长——每发现一个假成功模式就补进来。

### B6 大文档（3000+ blocks）的发布/删除走 UI，HTTP API 不可靠
- gen_publish_url 对 220+ 页文档不推进 version（08-19 实测 5 分钟不动）；UI 点「再次发布」60 秒完成（同样端点，浏览器会话上下文差异）。
- 膨胀大页面（4823 children）API 删不掉，只能 Playwright UI 删或新建文档。
- **规则**：大文档发布 = Playwright 打开分享面板点按钮；HTTP API 只用于小文档或作为第一尝试。

### B7 会话压缩丢上下文：长任务必须落盘任务护照
- 08-21 交接靠 TASK-SOP.md「2026-08-21 紧急交接」段；08-24 当前会话压缩后靠 memory + skill 恢复。
- **规则**：超过一个会话的任务，关键结论落盘到 `~/.hermes/tasks/<task>/TASK-SOP.md`，会话里只留指针。
